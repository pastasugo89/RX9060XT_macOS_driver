# AMDHV audit (read-only)

Date: 2026-11-25. Repo: https://github.com/mxtpasontop/AMDHV (clone: `research/ext/amdhv`, clone only; nothing built or run; no commits, no edits to tracked files).

## 1. What it is

AMDHV is an experimental x86_64 kernel extension (a Lilu plugin) that tries to make Apple's AppleHV / Hypervisor.framework backend work on AMD CPUs by translating the Intel VMX interface into AMD SVM. The repo's own description: "Experimental VMX-to-SVM translation for macOS on AMD. Diagnostic-only; native virtualization remains disabled."

It is a hypervisor-enablement project, not a GPU tool, not a VM/GPU passthrough tool, not a CPU microcode patch and not a cheat or exploit. Its README states it "does not yet provide working Hypervisor.framework virtualization on AMD hardware"; full translation and trap installation are blocked and the framework entry returns failure.

Scope of code (about 8.8k lines C/C++/asm, 1.4k lines Python):
- `src/AMDHV.cpp`: Lilu plugin entry, boot-arg mode handling, kext/patcher callbacks.
- `src/SVMCPU.cpp`, `src/SVMTransition.S`, `src/AMDSVM.hpp`, `src/VMCBTranslator.cpp`: SVM enable/restore, VMCB translation, the `clgi/vmload/vmsave/stgi` transition assembly.
- `src/NPTManager.cpp`, `src/EPTSource.cpp`, `src/GuestMemory.cpp`: shadow nested page tables and ownership checks.
- `src/SoftVMCS.cpp`, `src/InstructionDecoder.cpp`, `src/TrapAdapter.cpp`: software VMCS and VMX instruction decoding.
- `tests/`: C++ model tests, Python tooling tests, a QEMU TCG harness (`tools/emulate_transition.py`).

Third-party material:
- `Headers/Lilu/kern_api.hpp`, `kern_patcher.hpp`, `kern_util.hpp` are not verbatim copies of Lilu. They are rewritten adapters (`kern_util.hpp` is replaced by an `AMDHV_KERNEL_BUILD` shim) that keep Lilu's API shape and drop the original vit9696 copyright headers. Upstream Lilu is BSD-3-Clause (`research/ext/Lilu-1.7.3-audit/source/LICENSE.txt`, "Copyright (c) 2016-2018, vit9696"). If any of these headers were reused, Lilu's notice would still apply, so use our own Lilu copy instead.
- Lilu and MacKernelSDK are fetched at build time from upstream by `tools/dependencies.py` at pinned commits (`dependencies.lock.json`). They are not vendored in the repo.

## 5. Safety flags

Checked by reading the code. Nothing was run.

**Kernel-level code, default-off.**
- The kext is a root-level kernel extension (`Info.plist`: `OSBundleRequired` Root, `IOResourceMatch` IOKit, Lilu dependency `as.vit9696.Lilu` 1.2.0).
- Boot-arg mode selects behaviour (`src/AMDHV.cpp` near lines 600-630; default `bootstrap`):
  - `bootstrap` (default): publishes service state and registers no Lilu callbacks or hooks.
  - `preflight`: registers Lilu callbacks and checks kernel and AppleHV symbols. `preflightRoutes()` (around lines 138-152) only calls `patcher.solveSymbol()`. It installs no hooks, and `onPatcherLoad` / `onKextLoad` return before any route call in this mode.
  - `trap` and `full`: `init()` (around lines 185-194) rejects them and sets `blocked-backend`.
- Execution gates are compile-time constants, all `false` (`src/BackendPolicy.hpp`: `compatibilityVerified`, `synchronizedOwnership`, `synchronousShootdowns`, `faultSafeTransition`, `architecturalControls`; `executionEnabled` is `constexpr false`). The `routeWithDiagnostics()` path that writes kernel patches is therefore unreachable in shipped code.
- The repo's `kern.hv_support` contract: diagnostic mode expects `kern.hv_support = 0` and skips guest execution.
- Still, loading the kext at boot runs kernel code, and the README records that "earlier experimental builds caused immediate boot crashes". Do not install it on the test machine.

**Pinned kernel does not match this machine.**
- `config/compatibility.json` pins Darwin 25.6.0 with kernel UUID `28267FD5-3E1E-3686-8A1C-E73E2466FCFB` and AppleHV UUID `3D8ED9BA-2C51-3C31-921B-674CA3C940C1`.
- The kernel at `/System/Library/Kernels/kernel` on this Mac (macOS 26.6.2, build 25G83, `xnu-12377.161.14~5`, Darwin 25.6.0) has UUID `39CC2C26-3F72-3565-89C4-94DFE36DFDF2`. The kernel UUID differs, so AMDHV preflight would reject this build, and its ABI spans (`config/abi.json`) are not valid for our system. I did not check the AppleHV UUID on this machine.

**Runtime behaviour and data.**
- No runtime network access and no downloads at runtime. The only network access is the build-time `git fetch` of pinned Lilu and MacKernelSDK (`tools/dependencies.py`).
- `tools/diagnose.py` reads `sysctl kern.hv_support`, `kern.bootargs`, `kern.bootsessionuuid`, `kern.osversion`, `ioreg -c AMDHV` and `kmutil showloaded`, and writes records to `diagnostics/` (gitignored, local only). These can include boot args and the boot-session UUID. They are not uploaded.
- `docs/VALIDATION.md`: "EFI/config deployment: No writes." No `sudo`, `nvram`, `bless` or EFI writes in the source or tools.
- `Makefile` line 138 ad-hoc `codesign` with `com.apple.security.hypervisor` for a smoke-test executable. The smoke test is built, not run.
- `tools/check_symbols.py` and `tools/verify_abi.py` call `nm` only. `tools/package_kext.py` writes under `build/`.

**Not flagged:** no cheat, anti-cheat bypass, exploit, EFI payload, or obfuscated code.

## 6. Usefulness for our project

Our open problems (from `docs/STATUS.md`): GPU interrupts, SDMA, VCN, GPU hang recovery and robust fault recovery, Metal gaps, display underflow, macOS updates, Discord and Music stutter.

- **GPU driver, display, Metal, recovery:** no relevance. AMDHV contains nothing about PCIe/MMIO of the RDNA4 part, GPU interrupts, SDMA, VCN, display or the Metal stack.
- **Ryzen 7 7700 / OpenCore setup:** marginal. The SVM setup and restore logic (`src/SVMCPU.cpp`, lines ~35-58: EFER.SVME and VM_HSAVE_PA handling with rollback) and the NPT notes (`src/NPTManager.cpp`) are a readable reference for SVM mechanics. Nothing here needs changing on our machine.
- **Debugging via a hypervisor (MMIO tracing of Apple's drivers, VM with passthrough, GPU reset):** not usable. The repo does not provide working virtualization, its trap installation is disabled, and it has no passthrough. If we want a hypervisor for MMIO tracing later, `research/ext/OSX-KVM`, `VM_MACOS.md`, and `research/reports/vm_host_setup.md` are the more relevant starting points, and they already exist in our tree.
- **Lilu plugin pattern:** we already hold a Lilu copy under its BSD-3 licence (`research/ext/Lilu-1.7.3-audit`). That is the right reference for any patcher work.
- **Apple symbol names and instruction spans** (`config/imports.json`, `config/abi.json`): pinned to a different kernel build than ours (see section 5). Low value, and our own macOS RE notes (`research/reports/macos_25G83_re.md`) cover our build.

**Verdict on usefulness: unrelated to the GPU driver, low value overall.** The only transferable item is the SVM mechanics reference. Do not load it on the test machine.
