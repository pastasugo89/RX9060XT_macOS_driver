# CPU/GPU optimization research and prepared refinement — 28 October 2026

## Scope and evidence

Machine: Ryzen7 7700, RX9060XT/Navi44, macOS26.6.2/25G83,2560x1440/120Hz. The current custom stack is Cobalt-derived Metal→Vulkan→RADV plus the Navi44 bring-up/display components. A functioning desktop and CPPC readback are established; stutters, application beachballs and an instantaneous upper-screen black flash remain user-observed. No universal or “perfect” optimization can be inferred from successful initialization or a microbenchmark. This report selects a concrete next candidate from measurements and documents what it does not establish.

## Primary-source findings and applicability

| Area | Primary evidence | Meaning for this machine |
|---|---|---|
| CPU autonomous control | [AMD-authored amd-pstate documentation](https://docs.kernel.org/admin-guide/pm/amd-pstate.html) | Autonomous mode uses the hardware-advertised limits and EPP hint. The hint trades responsiveness against energy use; a lower value is not evidence of a better overall profile. The installed driver already requests autonomous operation and verifies all16CPU requests at EPP128. |
| CPU core selection | Same AMD document, preferred-core section | Firmware rankings inform a cooperating scheduler. A macOS MSR policy plugin alone does not implement Linux preferred-core scheduling. Spoofing a CPU identity or forcing clock maxima does not establish that capability. |
| GPU clock policy | [AMDGPU thermal/power controls](https://docs.kernel.org/gpu/amdgpu/thermal.html) | Dynamic auto selection and fixed profiling states serve different purposes. Forcing peak clocks disables relevant power behavior and is a profiling intervention, not a proven permanent desktop fix. Linux sysfs names are not macOS control interfaces. |
| Submission overhead | [Apple: command buffers](https://developer.apple.com/library/archive/documentation/3DDrawing/Conceptual/MTLBestPracticesGuide/CommandBuffers.html) | Too many submissions increase CPU/synchronization overhead; too few can starve the GPU. Our plugin must preserve the command boundaries and callbacks supplied by WindowServer/apps. Arbitrarily merging them would require a new correctness design. |
| Reuse | [Apple: persistent objects](https://developer.apple.com/library/archive/documentation/3DDrawing/Conceptual/MTLBestPracticesGuide/PersistentObjects.html) | Repeated allocation/compilation in the render loop is expensive. Existing descriptor/import/memory caches and pipeline caches should be preserved; observed classification and logging work can be reduced without changing rendering. |
| Frames in flight | [Apple: triple buffering](https://developer.apple.com/library/archive/documentation/3DDrawing/Conceptual/MTLBestPracticesGuide/TripleBuffering.html) | CPU and GPU need different reusable resources until completion. Increasing buffering without limits adds latency and memory pressure. Existing three-slot scanout plus kernel reusable-slot checks must remain intact. |
| Memory ordering | [Khronos synchronization specification](https://docs.vulkan.org/spec/latest/chapters/synchronization.html) | Submission order alone does not provide every execution/memory dependency. Barriers/fences cannot be removed just to lower measured CPU time. The candidate retains them. |
| Threading | [Khronos threading guide](https://docs.vulkan.org/guide/latest/threading.html) | Externally synchronized pools/queues need serialization or independent pools. Making the global Vulkan queue lock disappear without changing ownership is not valid optimization. The sampled queue-lock wait is already small relative to the observed main-thread work. |
| Pipeline reuse | [Khronos pipeline cache guide](https://docs.vulkan.org/guide/latest/pipeline_cache.html) | Serialized pipeline state can avoid repeated compilation across runs, subject to compatibility. Retain backend UUID/device/key checks; do not transplant another GPU's binary cache. |
| Shader back end | [Mesa RADV documentation](https://docs.mesa3d.org/drivers/radv.html) | SPIR-V is lowered through NIR to the ACO back end. An NVIDIA NVK/NAK replacement is not interchangeable with this AMD pipeline. Preserve the inspected matching RADV build. |
| Display | [AMDGPU DCN overview](https://docs.kernel.org/gpu/amdgpu/display/dcn-overview.html) | Scanout crosses memory arbitration, planes, output timing and link blocks with ASIC-specific configurations. A momentary band is not enough to identify a single refresh or memory-clock register to change. |
| Cobalt64 | [Source and scope](https://github.com/Almosst-DEV/Cobalt64), [changes](https://github.com/Almosst-DEV/Cobalt64/blob/main/CHANGES.md) | Remote HEADd1f7bad is the already-audited snapshot. The tested RX9070XT profile is a reference, not a Navi44 hardware oracle. Our native path already uses asynchronous presentation and retained safe slots. |
| NullMoth | [Changelog](https://github.com/nullmoth/nvidia-macos-driver/blob/main/CHANGELOG.md), [current framebuffer source](https://github.com/nullmoth/nvidia-macos-driver/blob/main/kexts/NVRMFB/fb/nvrm-fb.cpp) | Examined at dd797fb. Useful designs include completion-driven presentation, bounded latch waiting, retained allocations with generation/cookie checks, and work kept outside cursor locks. Its NVIDIA NVKMS code/clock controls are not copied into the AMD driver. |

## What the actual profiling selects

The first-boot report records live samples, not an assumed bottleneck. WindowServer's main thread repeatedly enters dladdr/findClosestSymbol from n48s_classify while creating CoreAnimation IOSurface wrappers. The five-second sample has91samples there,87in symbol lookup. Negative surface classifications are deliberately not retained: the same surface can later be requested by the actual display caller. Caching those negative surface decisions would be incorrect.

Commit cce3289 instead caches exact return-PC symbol predicates only for immutable dyld shared-cache images. It retains full-PC collision checks, excludes unloadable images, uses the existing lock, preserves negative-surface reconsideration and keeps the first stack dumps. It also rate-limits six normal diagnostic sites seen on frequent allocation/encoding paths; error and fallback logs stay enabled. A local CoreFoundation-only lookup benchmark strongly reduces this narrow cost, but cannot predict a percentage desktop speedup.

The prepared refinement also includes10newly observed shader pairs. Fourteen runtime translations have independently checked input AIR SHA256 keys; four already match bundled pairs byte-for-byte. Only the10absent keys are added. Every combined SPIR-V module is validated for Vulkan1.2 and every module has a metadata sidecar. This avoids AIR translation waits for those exact paths after cache loss/a cold start. It does not make arbitrary future shaders supported, nor does a valid SPIR-V module prove its full rendering semantics.

CPU decision: retain the verified autonomous policy, hardware lowest/highest bounds, desired0 and EPP128. No MSR, voltage, PPT/thermal limit, core topology, boost limit or scheduler patch is changed by this package. Further EPP tuning needs comparable workload latency, energy and thermal measurements; none presently proves that a different value is an improvement. The included read-only CPPC checker can verify policy/readback after deployment.

## Prepared fix and deployment boundary

`tools/baremetal/navi44-desktop/prepare-performance-fix.py NEW_DIRECTORY` prepares the revision25 bundle, validates shader resources/signature and generates a matching Stage23 boot guard with the final executable hash. `--check` independently rechecks package content, signature, shell syntax and the unchanged installed bundle24/boot-script baseline. The package contains only the Metal bundle and its coordinated activation script as system targets, plus review/verification material. It is not the earlier Stage22 whole-EFI installer payload and must not be passed to that installer or installed by copying the bundle alone: the boot guard must change with it. No EFI, CPU kext, Bluetooth driver or live service is changed by preparation/checking.

Existing boot-state recovery remains intact. A pending/failed activation cannot be cleared merely by changing the profile name. Hardware verification still requires a coordinated installation and a user-controlled reboot; preparation is not activation. The current Stage22 driver remains installed until that later step.

## Acceptance gates and remaining work

Before reporting a speed improvement: compare the same window/app actions, cold and warm starts, main-thread classification time, CPU usage, frame timing distribution and resource growth on24and25. A cache lookup microbenchmark is only mechanism evidence. App event waits and missing API paths must be measured separately from WindowServer throughput. Existing G2/G4/G5 admission limits remain; general GPU memory-budget changes need allocation/failure evidence.

Before reporting black-band removal: capture a visible event with presentation/scanout/underflow timing or establish a reproducible A/B. The120Hz-only mode table prevents a standard60Hz A/B. A30second read-only register sample showed no current underflow or VM fault, but the historical sticky OPTC bit was already set. Removing fences, forcing clocks, clearing status blindly or changing unsupported timings would not supply the missing proof. This candidate does not claim to fix the band.

Bluetooth keyboard discovery/pairing and AirDrop remain distinct open work. The selected Qualcomm Wi-Fi source lacks AWDL; GPU/CPU optimizations do not supply it. All source modifications and preparation tooling are committed; raw identifying system captures stay ignored.
